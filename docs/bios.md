# BIOS findings

## Baseline and high-level result

Compared Valve F7A0133 from its official SteamOS package server with DeckSight
r03 and r04. Exact inputs are pinned in [artifacts.json](../research/artifacts.json).
All offsets below refer to the extracted **16 MiB BIOSIMG**, not the `.fd` file.
BIOSIMG begins at container offset `0xe8c70` in these three inputs.

**Verified offline:** stock→r03 changes 4,988,315 BIOSIMG bytes; r03→r04 changes
572 bytes. Most stock→r03 differences are compression consequences of replacing
the splash image, not millions of bytes of changed executable code.

UEFIExtract A75 decompressed both stock and r04. Comparing the parsed FFS file
CRC fields finds only the compressed-volume container and the splash file
`F0DA323C-43A4-48DB-AEFE-CB314F7F5F6E` changed, in both firmware halves.
Comparing extracted leaf bodies also finds padding/free-space changes. No other
parsed executable module changes were observed. The parser emits the same kinds
of alignment/raw-area/Volume Top File warnings on stock and modified images;
this is evidence limited to what the tool successfully parsed.

The INI_IMG contents are identical. BIOSCER differs. The outer DRV_IMG contains
the inner images, so a changed DRV_IMG hash alone does not establish that the
flasher executable changed. Signing and trust enforcement have not been validated.

### Container certificates and executable sections

Additional PE inspection establishes that `.text`, `text`, the unnamed section
and `.xdata` match byte-for-byte in both the outer container and embedded
DRV_IMG. Their `.reloc` sections include firmware payload data and differ.
PE length/checksum/certificate-directory fields also change. See the
[stock](../research/reports/stock-container.json) and
[r04](../research/reports/r04-container.json) reports.

Both outer and embedded r04 PKCS#7 certificate bundles report subject and issuer
`CN=QA Certificate.`; stock reports `CN=Jupiter`. Certificate metadata was read
with `openssl pkcs7 -print_certs`; cryptographic signature validity, chain trust
and the updater's acceptance policy have **not** been tested. This is not
evidence of a Valve-authorized signature, a recovered signing key or a usable
open signing pipeline. It establishes another changed artifact to investigate.

## EC changes

There are two 128 KiB EC regions at BIOSIMG offsets `0x00000` and `0x40000`.
Apply the following relative offsets to each base. The stock copies are identical.

| Relative offset | Stock → DeckSight r04 | Evidence / interpretation |
| --- | --- | --- |
| `0x68e5..0x6964` | Replace 128-byte EDID | DSO:5001, DeckSight, portrait 1080×1920 |
| `0x6967` | `06 → 0a` | DPCD MAX_LINK_RATE: 1.62 → 2.7 Gbit/s; r03 used `0f` |
| `0x696d` | `06 → 14` | Second link-configuration table field; exact role unresolved |
| `0x69ae..0x69d9` | Modify ANX SPI timing table | Active 1080×1920; H FP/sync/BP 136/1/24; V 20/1/15; nominal 80 Hz |
| `0x69d3` | `48 → 44` | Panel transfer-mode field changes 2→1, consistent with burst→non-burst sync events; r03 retained `48` |
| `0x6e55..0x6ed6` | Replace first 26 five-byte command records | New panel initialization; ends with `ff 00000000`; original unused tail remains |
| `0x7dcf..0x7ece` | Replace `ff` space with 256-byte EDID | Relocated base block plus CTA HDR block |
| `0xf2d2` | `02 → 01` | 8051 `MOV A,#2` becomes `MOV A,#1` in display selection |
| `0xf37d..0xf37e` | `68 e5 → 7d cf` | 8051 code's EDID base address changes |
| `0xf3ad` | `7f → ff` | EDID copy-loop limit grows from 127 to 255 |
| `0x1f7fe..0x1f7ff` | `c208 → e16a` | Big-endian additive checksum of bytes `[0x2000,0x1f7fe)` |

Outside the EC and compressed UEFI volumes, the BIOS version string gains
` DS` at `0x6a8015` and `0xea8015`.

### EDID details

The r04 extended EDID is generated by `r04_edid()` and reproduced byte-for-byte.
The old 128-byte location also declares an extension, but its immediately
following bytes are link tables, not CTA data. The EC reader is redirected to
the valid 256-byte copy at `0x7dcf`; scanning the old location as a full EDID
therefore correctly reports an invalid extension checksum.

- Vendor DSO, product `0x5001`, EDID 1.4, monitor name DeckSight.
- One 1080×1920 DTD: 143.18 MHz, ~60.0003 Hz, H 32/8/100, V 8/2/26.
- CTA HDR static metadata payload `06 05 01 6a 6a 00`: SDR and PQ flags,
  static metadata type 1, maximum and frame-average luminance codes 106
  (approximately 496.74 cd/m²), minimum code 0.
- r03's 80 Hz DTD is removed. Gamescope's public Lua separately advertises
  40–80 Hz with different timings and 800/700-nit metadata. These declarations
  are not measured luminance or proof that all refresh rates initialize reliably.

### Initialization commands

The table consists of a register byte and a four-byte value. For the first EC
bank the values are stored big-endian. The register sequence and values are
named in `R04_PANEL_INIT` in `opendecksight/firmware.py`.
`0x70` is the bridge payload register, `0x6c` its packet header, `0xaa` a delay,
and `0xff` the terminator. The table includes sleep-out, control-display `0x53`,
brightness `0x51`, tear-control, display-on and vendor-specific commands.
Vendor-specific fields are preserved as observed values, with no invented names.

From r03 to r04, control-display changes `0x61→0x69`, and a six-byte long-write
payload beginning with brightness `0x51` changes from `51 99 19 99 19 c4` to
`51 09 00 00 00 00`. Runtime brightness uses a three-byte payload instead.
The effect of the additional initialization parameters needs validation.

## Important anomaly: opposite byte order in the second EC region

**Verified offline:** in both r03 and r04, the second EC region stores the
four-byte values in these 26 new records in reverse order relative to the first.
For example, r04 starts with `70 00 a5 a5 9c` in the first EC region and
`70 9c a5 a5 00` in the second. The surrounding interpreter code is identical.
The stock command tables use the same byte order in both copies.

**Interpretation:** this resembles an accidental repeated byte-swap while
building two images. It is not yet known whether that copy is used, when it is
selected, or whether it contributes to any display issue. An additive checksum
cannot detect a byte permutation, so both regions have the same valid checksum.

The reproduction intentionally preserves this mismatch. A corrected second
bank would be a separate experimental change requiring recovery capability and
hardware validation, not something to slip into a claimed exact reproduction.

## Open implementation and limits

`build_r04_ec_reproduction()` accepts only the pinned stock BIOSIMG hash, creates
the EDID and tables from source, changes the identified EC instructions, and
recomputes both checksums. Both resulting EC regions have been compared in full
with r04 and match exactly. The stock logo, version and UEFI remain intact.

This does not rebuild EC firmware from source: it applies documented changes to
Valve's existing EC program. It does not create a signed `.fd`, replace the
Insyde/AMD platform firmware, or establish bootability. The old 8051 interpreter,
touch controller firmware and many panel-specific command meanings remain
outside the reconstructed source.
